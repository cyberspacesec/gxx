# GXX 指纹数据与验证

GXX 的规则目录与扫描结果分别表达规则来源、产品信息、提取结果和测试状态。调用方通过 `RuleCatalog` 导入完整规则目录，通过 `TargetResult.Matches` 保存原始命中，通过 `TargetResult.Products` 展示归并后的产品。公共字段和使用示例见 [SDK 使用文档](../sdk/sdk.md)。

## 数据约定

| 信息 | SDK 字段 | 语义 |
|---|---|---|
| 规则作者 | `Info.Author` | YAML 作者，不作为厂商 |
| 产品声明 | `Info.Product`、`ProductCatalog()` | 规则 `info.product` 的声明：稳定产品 ID、规范名称、厂商、分类、身份、可信度、标签、别名、参考资料及有依据的 CPE |
| 产品厂商 | `Info.Vendor`、`Info.Product.Vendor` | 产品声明的厂商；未知时为空 |
| 产品身份 | `Info.Product.Identity` | `product` 命中即确认是这个产品；`signal` 只是技术线索 |
| 产品可信度 | `Info.Product.Assurance` | `verified` 厂商与产品已确认且有可访问的官方链接；`inferred` 由规则名称与特征推断 |
| 服务声明 | `Info.Services` | TCP/UDP 规则识别的协议、传输层与端口 |
| 附加元数据 | `Info.Metadata` | 规则 `info.metadata` 的副本，引擎只透传 |
| 来源验证声明 | `Info.Verified`、`Info.VerificationStatus` | 区分来源已验证、未验证与未声明 |
| 样本记录 | `Info.Validation` | 测试方法、样本数、复核日期与适用范围 |
| 置信度 | `Info.Confidence` | 经外部数据校准的值；未知时为 JSON `null` |
| 规则来源 | `Info.Source` | 文件路径、实际字节 SHA256 与规则包源版本 |
| 产品版本 | `ProductVersion`、`ProductVersions` | 成功子规则的 `output.product_version`；冲突时不返回单一确定版本 |
| 检测证据 | `MatchedRules[].Evidence` | 实际执行分支的表达式、字段、片段与字节位置 |
| 质量缺项 | `RuleCatalog()[].MissingMetadata` | 尚需补充或核实的数据项，不代表规则失效 |

产品信息以规则自带的声明为准，产品 ID 不按规则作者或 HTTP 传输协议猜测；同一产品 ID 在所有规则中的声明完全相同，加载内置库时检查。`sdk/catalog.json` 由 `go generate ./sdk` 从 `fingerYaml/` 生成，测试断言二者逐字节一致。CPE 只表示产品映射，不代表发现 CVE 或漏洞。创建时间、来源验证声明、产品可信度与当前样本复核日期分别保存，互不替代：规则的 `verified: true` 是规则来源的声明，产品的 `assurance: verified` 是对产品归属的确认，二者都不等于经过样本测试。规则版本与产品版本不能混用。

`identity: signal` 用于语言、前端库、通用框架特征、默认页面、只能识别出厂商的页面（产品 ID 为 `<厂商段>.vendor-mark`）、无品牌的通用特征（`generic.<特征>`）和页面中嵌入的第三方组件；调用方可只展示 `product`，把 `signal` 作为技术栈线索。`assurance: verified` 的产品同时满足：厂商与产品已确认、整理时把握程度为高、`references` 至少有一个经实际访问可用（HTTP 状态小于 400）的官方主页或官方仓库；其余为 `inferred`，表示由规则名称与匹配特征推断，厂商或产品名可能需要人工核实。不可访问的链接不写入规则。

ARL 的 `web-arl` 与 `web-资产灯塔系统` 两条 v1.7.0 规则的子规则与总表达式完全相同，合并为 `arl`，后者的名称保留在别名中。版本冲突时保留全部有限版本候选并标记 `VersionConflict`。未声明产品的规则（调用方自有规则）按规则分别展示，产品 ID 留空，不合并同名猜测结果。

v1.7.0 的 2,349 个旧规则标识与新标识的对应关系见 [指纹标识对照表](指纹标识对照表.csv)（`old_id,old_path,new_id,new_path,product_id,action`，`action` 为 `renamed` 或 `merged`）。每条规则的产品、身份、可信度、整理时的把握程度（`high`、`medium`、`low`）与规则疑点见 [指纹核对表](指纹核对表.csv)；疑点只记录规则本身条件过宽、规则名与实际匹配不符或混入其他产品特征等问题，不修改规则正文，留待人工决定。

`inferred` 的产品信息以及缺少厂商、参考资料和专项测试记录的规则仍属于待核实数据，`MissingMetadata` 分别标为 `product-assurance`（1,970 条）、`vendor`（1,123 条）、`references`（1,884 条）、`sample-validation`（2,341 条）、`version-extractor`（2,342 条）、`tags`（726 条）。目录接口对全部规则提供相同结构和缺项说明，不能把完整接口覆盖解释为全部产品元数据已经核实。通用描述和来源未验证也不能直接解释为规则无效。

产品参考资料只引用官方产品主页、官方文档和维护仓库；没有可追溯依据时保留空值。空引用、含账号信息的链接与 `example.com` 占位链接不作为产品依据。Apache HTTP Server、WordPress 和 Fastjson 的 CPE 对照 [NVD CPE 字典](https://nvd.nist.gov/products/cpe) 的产品记录；不自动生成其他产品的 CPE。每个产品的直接资料链接保存在 `ProductInfo.References`。

## 样本与回归测试

`sdk/product_integration_test.go` 使用本机可控 HTTP 服务，逐样本执行全部 2,348 条规则。35 个样本共完成 **82,180 个规则任务、385 次 HTTP 请求**，任务失败为 0。专项记录保存在 `sdk/validations.json`，绑定执行样本时实际加载的规则文件 SHA256；文件内容变化后旧记录不再适用，须重新执行样本并由测试据实写入：

```bash
go test ./sdk -run '^TestFullCorpusProductSamples$' -update-validations
```

| WordPress | `wordpress` | 4 | 1 | generator 版本、大小写、静态资源与版本缺失；排除 Drupal 版本串用 |

| Jenkins | `jenkins` | 2 | 2 | 专有响应头与代理协议；排除普通版本文本 |
| nginx | `nginx` | 3 | 2 | Server 产品边界、大小写、隐藏版本；排除 nginx-webui |
| ARL | `arl` | 1 | 1 | 标题特征与合并后的单一来源 |

`sample-tested` 只表示上述有限合成样本通过，不表示真实部署的准确率或召回率，置信度保持未知。Fastjson 使用类名特征，普通 `JSON.parse` 和通用 `unclosed string` 不再构成产品识别依据；Jenkins 使用实际存在的专有响应头，避免把 `*` 当作包含匹配的通配符。

内置库测试（`fingerYaml/library_test.go`、`sdk/metadata_internal_test.go`）检查：全部规则可加载；规则标识唯一且合规；文件位于 `<分类>/<规则标识>.yaml` 且分类与产品声明一致；每条规则通过严格校验；同一产品的声明一致；`verified` 的产品都有参考链接；`catalog.json` 与规则文件一致；专项记录只指向存在的规则且摘要与文件一致；对照表覆盖 v1.7.0 的全部 2,349 个旧标识，核对表与对照表逐行对应。

其他回归覆盖：全部 6,034 个 CEL 表达式编译；证据开关下的完整命中和产品版本一致；AND、OR、NOT 实际分支及短路；Unicode 字节位置、二进制片段与正文末尾命中；提取失败、失败子规则、版本冲突与结果预算；并发实例、输入副本、返回值副本、规则重载和摘要失效；图标哈希、完整图标读取、标题与 ICP 提取。完整样本测试不替代逐产品真实部署测试。

## 资源与性能

匹配证据使用固定追踪区，只记录实际布尔结果，不重放 CEL、请求、等待或随机函数。执行计划保存字段和定位条件，不保留完整 AST。定位在成功分支上进行，片段复制为独立有界数据，SDK 结果不持有完整正文。每条子规则最多 16 个证据、每个片段最多 256 个原始字节，每次表达式最多 128 个布尔节点，每条指纹最多 64 个成功子规则，超出时提供截断标记。

正文读取上限为 512 KiB，图标哈希采用完整流读取。图标哈希算法、编码行宽、补齐和换行语义保持一致。正则字符缓冲与响应归一化共用单目标 8 MiB 的估算缓存预算；执行状态、请求配置、缓存作用域及目录覆盖独立属于 Engine。只读编译程序可以共享，调用方输入和返回的可变数据不跨实例共享。

2026-10-01，macOS / Apple M2 / Go 1.25.0，依赖版本不变。基线为 `5f42188` 的 2,348 条规则，被测实现为 2,349 条规则；本机固定 Apache / WordPress 响应，默认 200 规则协程和 5 目标并发，每个进程预热一次后扫描 50 个目标，基线与被测实现交替测量三组。以下为三组中位数；累计分配包含同进程 HTTP 靶场，峰值 RSS 包含启动和规则加载，不等于长期存活堆或 IDE 内存：

| 指标 | 小响应基线 | 小响应被测 | 256 KiB 响应基线 | 256 KiB 响应被测 |
|---|---:|---:|---:|---:|
| 50 目标 HTTP 请求数 | 750 | 700 | 750 | 700 |
| 规则任务数 | 117,400 | 117,450 | 117,400 | 117,450 |
| 50 目标总耗时（ms） | 154.07 | 187.20 | 743.60 | 814.24 |
| 累计分配量（MiB） | 47.20 | 38.83 | 449.71 | 462.42 |
| 分配对象数 | 1,248,195 | 1,064,892 | 1,360,311 | 1,166,801 |
| 预热并 GC 后存活堆（MiB） | 18.95 | 21.56 | 22.51 | 26.00 |
| 扫描后 GC 存活堆（MiB） | 20.45 | 22.84 | 24.36 | 26.69 |
| 进程峰值 RSS（MiB） | 76.44 | 80.83 | 126.33 | 132.70 |

50 目标请求缓存统计扣除预热后：当前命中 183,600 次、未命中 500 次，命中率 99.7284%；基线命中 183,700 次、未命中 550 次，命中率 99.7015%。命中统计不是网络请求计数，图标和基础探测等请求由靶场独立计数。扫描结束后缓存条目和跟踪 URL 均为 0。

单目标 `BenchmarkFullFingerprints` 的三组测量中，小响应累计分配中位数约 0.71 MiB，分配对象约 21,154；256 KiB 响应约 12.80 MiB、21,874 个对象。基准的 HTTP 服务与并发目标测试不同，不能混用两组绝对值。复核命令：

```bash
GOTOOLCHAIN=go1.27.4 go test ./sdk -run '^$' -bench '^BenchmarkFullFingerprints$' -benchmem -benchtime=1s -count=3
```

默认详情回传包含产品信息和证据执行计划，有固定常驻成本。测量中的小响应累计分配与请求数下降，但并发耗时、常驻堆和部分大响应分配增加，不能宣称所有指标都下降或已经达到性能极限。无需证据详情的调用方可使用 `WithMatchDetails(false)`，产品版本、元数据和命中结果仍回传；消费大量目标时使用 `ScanCallback` 或 `ScanIterator`，避免一次保留全部结果。

2026-11-22，同一台 Apple M2、Go 1.27.4，`BenchmarkFullFingerprints` 交替运行 6 组取中位数：v1.7.0（2,349 条规则）与当前（2,348 条规则，带产品声明）的小响应单目标全量扫描为 2.163 → 2.176 ms，256 KiB 响应为 8.905 → 9.036 ms，每次扫描的分配对象数为 5,750 → 5,788 与 6,002 → 6,031。执行清单先派发需要自己发请求的规则，扫描耗时不随规则文件在库中的排列而变。

## 目录维护

产品信息写在规则的 `info.product` 中，字段与一致性要求见[指纹规则格式说明](指纹规则格式说明.md#产品声明)。新增或修改产品声明后执行 `go generate ./sdk` 重新生成 `sdk/catalog.json`，同一产品的多条规则必须复制完全相同的声明。系统扩展目录使用 `WithProductCatalog`，以明确的 `RuleIDs` 按规则追加或覆盖产品声明，同一规则不能出现在两个目录项中；覆盖已有产品时列出它的全部规则。专项记录使用 `WithRuleAssessments`，包含规则 ID、SHA256、方法、样本数及范围；只有摘要一致时应用。来源版本通过 `WithRuleSourceVersion` 声明，不能覆盖原生内置来源的实际版本。

修改检测条件或输出表达式后，先检查普通页面、相似产品和缺失版本的阴性样本，再检查阳性响应，并重新执行样本更新专项记录。`.gitattributes` 对 YAML 禁用 Git 自动换行转换，使跨平台 SHA256 一致。产品参考资料变化应复核实际链接，未知信息不能用作者、占位链接或默认置信度补齐；`assurance` 只在厂商与产品确认且有可访问的官方链接时改为 `verified`。
