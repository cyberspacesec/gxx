# GXX 指纹规则格式说明

## 指纹文件结构

- **文件格式**: YAML
- **文件扩展名**: .yaml（引擎同样读取 .yml；内置库统一用 .yaml）
- **编码**: UTF-8
- **内置库目录**: `fingerYaml/<产品分类>/<规则标识>.yaml`，分类与 `info.product.category` 相同

## 基本结构

```yaml
id: 指纹规则的唯一标识符

info:
  name: 指纹名称，描述识别的目标系统或组件
  author: 规则作者
  verified: false # 是否经过验证
  description: |
    详细描述指纹对应的系统或组件，
    支持多行文本
  reference:
    - 参考资料链接，可以是官网、CVE链接等
    - 支持多个参考链接
  tags: cve,web,apache,ssh # 标签，用逗号分隔，便于分类和检索
  created: 2025/04/01 # 创建日期，格式为YYYY/MM/DD
  product: # 产品声明，见下方“产品声明”
    id: vendor.product # 厂商段.产品段
    name: 规范产品名
    vendor: 厂商规范名 # 不确定时省略
    category: application
    identity: product # product：命中即确认产品；signal：技术线索
    assurance: inferred # verified：已确认并有官方链接；inferred：推断
    tags: [oa]
    references: [] # 官方链接；assurance 为 verified 时必填
  services: # TCP/UDP 规则必填，HTTP 规则可省略
    - protocol: ssh
      transport: tcp
      ports: [22]
  metadata: {} # 任意附加信息，引擎只透传

set:
  # 变量定义，用于后续规则中引用
  num: randomInt(800000000, 1000000000) # 生成800000000到1000000000之间的随机数
  payload: randomLowercase(20) # 生成20个随机小写字母
  hostname: request.url.host # 获取目标主机名
  host: request.url.domain # 获取目标域名

rules:
  # 规则定义，每个规则包含请求和匹配表达式
  r0: # 规则ID，通常以r0, r1, r2...命名
    request:
      type: http # 请求类型（http/tcp/udp），HTTP请求可省略
      method: GET # 请求方法，默认GET
      path: / # 请求路径，默认/
      headers: # 请求头，可选
        User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
        Content-Type: application/json
      body: '{"key": "value"}' # 请求体，POST请求时使用
       follow_redirects: true # 是否跟随重定向，默认true（程序端默认跟随）
    expression: response.status == 200 && response.body.bcontains(b"特征字符串") # 匹配规则表达式

  r1:
    request:
      method: GET
      path: /admin
    expression: response.status == 302 || response.headers["Server"].contains("Apache")

  r2:
    request:
      method: GET
      path: /{{num}}.php # 使用set中定义的变量
    expression: response.body.bcontains(b"404") || response.icon_hash == "1236214049"

# 最终判断表达式，组合多个规则的结果
expression: r0() && (r1() || r2())
```

## Info 字段详细说明

| 字段           | 描述                                          | 必填  | 示例                                  |
|---------------|----------------------------------------------|------|--------------------------------------|
| name          | 指纹名称，描述目标系统或组件                      | 是    | "Apache Tomcat"                     |
| author        | 规则作者                                       | 是    | "zhizhuo"                           |
| verified      | 规则来源的验证声明；缺省时状态未知                  | 否    | true/false                          |
| description   | 详细描述指纹对应的系统或组件                      | 是    | "Apache Tomcat 应用服务器识别"        |
| reference     | 参考资料链接数组                                | 否    | ["https://tomcat.apache.org/"]      |
| tags          | 标签，用逗号分隔                                | 否    | "web,apache,tomcat"                 |
| created       | 规则创建日期                                   | 是    | "2025/04/01"                        |
| product       | 规则识别的产品，字段见下方“产品声明”              | 标准格式必填 | 见下文                          |
| services      | TCP/UDP 规则识别的服务                          | TCP/UDP 规则必填 | 见下文                       |
| metadata      | 任意映射，引擎只透传，不参与匹配                   | 否    | `{owner: team-a}`                   |

`author` 是规则作者，不是产品厂商。产品名称、厂商、分类、别名、CPE 和产品参考资料写在规则自己的 `info.product` 中，SDK 的产品信息与产品目录都由它得出。规则声明 `verified: true` 只表示规则来源的验证声明，与产品声明的 `assurance` 无关，也不等于经过当前样本测试，样本记录和置信度见[指纹数据与验证](指纹数据与验证.md)。

## 规则标识

`id` 由小写字母、数字与单个连字符组成，长度 3–96，在规则库内唯一。内置规则的标识由产品键派生：`.` 换成 `-`，厂商段与产品段相同时只保留一段（`nginx.nginx` → `nginx`，`weaver.e-cology` → `weaver-e-cology`）；同一产品有多条规则时，一条用基础标识，其余追加说明识别方式的后缀（如 `-login`、`-default-page`、`-console`、`-api`）。v1.7.0 的旧标识与新标识的对应关系见 [指纹标识对照表](指纹标识对照表.csv)。

## 产品声明

`info.product` 声明规则识别的产品：

```yaml
info:
  name: 泛微 e-cology
  product:
    id: weaver.e-cology
    name: e-cology
    vendor: 泛微网络
    category: application
    identity: product
    assurance: verified
    tags: [oa]
    aliases: [泛微OA, ecology]
    references: [https://www.weaver.com.cn/]
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `id` | 是 | `厂商段.产品段`，恰好一个点，各段由小写字母、数字与连字符组成，首字符为字母或数字，总长 ≤ 96 |
| `name` | 是 | 规范产品名，1–200 个字符；中文产品保留中文名 |
| `vendor` | 否 | 厂商规范名；不确定时省略，不用规则作者填补；社区或开源项目没有公司主体时省略 |
| `category` | 是 | `application` `middleware` `framework` `operating-system` `cms` `database` `web-server` `security` `library` `hosting-panel` `device` `network-device` `iot` `other` |
| `identity` | 是 | `product`：命中即确认是这个产品；`signal`：技术线索（语言、前端库、通用框架特征、默认页面、只能识别出厂商的页面、无法对应具体产品的通用特征） |
| `assurance` | 是 | `verified`：厂商与产品已确认，且 `references` 至少一个可访问的官方链接；`inferred`：由规则名称与特征推断 |
| `tags` | 否 | 产品级用途标签，≤ 8 个，小写字母、数字与连字符（如 `oa`、`vpn`、`firewall`），不重复 |
| `aliases` | 否 | 别名与旧名，≤ 16 个，不为空、不重复 |
| `cpe` | 否 | CPE 2.3 格式化字符串；只在有依据时填写，不自动生成 |
| `references` | `verified` 必填 | 官方主页、文档或仓库的 http(s) 链接，≤ 16 个；不含账号信息，不用 `example.com` 等占位域名 |
| `description` | 否 | 产品简介，≤ 500 个字符 |

**一致性**：同一个 `product.id` 在所有规则中的声明必须逐字段完全相同。加载内置库时检查；引擎加载任何规则集（含 `WithProductCatalog` 的覆盖）时也检查，不一致即加载失败，错误为 `ProductConflictError`，指出产品标识、两条规则和第一个不同的字段。SDK 的产品目录 `sdk/catalog.json` 由规则生成，不手工维护。

产品键的约定：厂商段优先用厂商公认的英文或品牌写法，没有时用不带声调的拼音；厂商未知时厂商段重复产品段（如 `act-manager.act-manager`）；只能识别出厂商、识别不出具体产品的规则用 `<厂商段>.vendor-mark`；完全没有品牌的通用特征用 `generic.<特征>`；页面中嵌入的第三方组件用该第三方自己的产品键。后三种的 `identity` 为 `signal`。默认页面归到真实产品名下，用规则标识的 `-default-page` 后缀区分。

## 服务声明

`info.services` 声明 TCP/UDP 规则识别的服务，每项为 `{protocol, transport, ports}`：

```yaml
info:
  services:
    - protocol: ssh
      transport: tcp
      ports: [22]
```

`protocol` 为应用层协议名，不能为空；`transport` 为 `tcp` 或 `udp`；`ports` 为常见端口，每个在 1–65535 之间。含 `type: tcp` 或 `type: udp` 子规则的规则必须声明；HTTP 规则可以省略。

## 附加元数据

`info.metadata` 是任意映射，供调用方保存自己的信息。引擎只透传（SDK 的 `FingerInfo.Metadata`），不参与匹配，内部的键不做校验。

## 校验

SDK 的 `sdk.ValidateRule` 不发请求即可校验一条规则。非严格模式与引擎加载的结论一致：YAML 无法解析或违反规则策略才是 error，其余为 warning，缺少 `info.product` 的规则仍可加载和匹配（调用方自有规则可以不声明产品），其产品信息为空。严格模式用于入库前检查，把下列问题报告为 error：`info` 中的未知键（`metadata` 内部除外）、规则标识不合规（`invalid-id`）、缺少产品声明（`missing-product`）、产品声明的字段不合规（`invalid-product`）、TCP/UDP 规则没有声明服务（`missing-services`）、服务声明不合规（`invalid-service`）以及缺少名称或表达式无法编译。内置规则库的每个文件都通过严格校验。

## 请求类型说明

### HTTP 请求

```yaml
type: http              # 可省略
method: GET/POST/PUT/DELETE/...
path: 请求路径，如 /login
headers:                # 可选
  User-Agent: ...
body: 请求体
follow_redirects: true  # 是否跟随 30x，默认 true；false 表示只匹配第一个响应
```

> **重定向**：规则请求默认跟随 30x（最多 5 跳），30x 可以指向其他主机、协议或端口；离开扫描目标后
> 规则里的请求头不再携带。`path: /` 的规则依次匹配入口跳转链上的
> 每一页（入口的 30x、跳转壳、最终页面），任一页满足即命中，同一条指纹的多条规则须在同一页上成立。
> `path` 以扫描目标的路径为前缀；`method` 省略时为 GET。详见[资产与跳转](资产与跳转.md)。

### TCP 请求

```yaml
type: tcp
host: 连接地址，如 "[{{domain}}]:22"（写法见下方说明）
data: 发送的数据，如 "test\n"
data-type: text          # 可选：默认 text，"hex" 表示按十六进制解码 data
read-size: 4096          # 可选：读取字节数上限
read-timeout: 5          # 可选：单次接收的总时长上限，单位秒
read-idle: 300           # 可选：收到数据后等待后续分段的空闲时间，单位毫秒；默认自适应
```

### UDP 请求

```yaml
type: udp
host: 连接地址，如 "[{{domain}}]:53"
data: 发送的数据
data-type: text          # 同上
read-size: 1024
read-timeout: 5
```

> **`type` 取值**：只支持 `http`（默认，可省略）、`tcp`、`udp`。其他取值（包括 `ssl`、`tls`、`go`）
> 在加载规则时直接报错，不会退回 HTTP。TLS 不是独立类型，由 `host` 的协议前缀或端口决定。
>
> **`host` 写法**：推荐在 `set` 中定义 `domain: request.url.domain`，再写 `host: "[{{domain}}]:22"`。
> `request.url.domain` 是不带端口的主机名或 IP；方括号使 IPv6 目标也得到唯一的地址，域名和 IPv4
> 加方括号同样合法。不要用 `request.url.host` 拼端口：目标自带端口时它是 `1.2.3.4:8080`，
> 拼出的 `1.2.3.4:8080:22` 会被拒绝。未加方括号且含多个冒号的地址（如 `2001:db8::1:22`）
> 无法区分地址与端口，一律报错。`host` 为空时直接连接扫描目标。
>
> **协议前缀与默认端口**：`host` 可带 `tcp://`、`udp://`、`http://`（明文）或 `https://`、`tls://`、
> `ssl://`（TLS）前缀，如 `"ssl://[{{domain}}]:8443"`。带前缀时省略端口按 TLS 取 443、明文取 80；
> 不带前缀时端口为 443 或省略端口视为 TLS（默认 443），其他端口为明文。
>
> **接收**：`read-timeout` 是单次接收的总时长上限。TCP 收到首段数据后最多再等 `read-idle` 毫秒
> 接收后续分段；未设置时取首段到达耗时的两倍，并限制在 100–1000 毫秒。服务端分段间隔较长
> （如多行横幅）时可调大 `read-idle`。UDP 每次接收一个数据报，不使用 `read-idle`。
>
> **代理**：TCP/UDP 请求遵循全局 `--proxy` / `WithProxy` 设置。TCP 可走 http/https/socks5/socks5h；
> UDP 仅支持 socks5/socks5h（经 SOCKS5 UDP ASSOCIATE），HTTP 代理 + UDP 会报错。
> 带 TLS 的 TCP（`https://`/443/`ssl://`）与 HTTP 路径使用同一套扫描 TLS 策略（最低 TLS 1.0 + 完整套件）。
> UDP 没有 TLS 通道：即使 `host` 写了 `https://`，也只取其端口并保持明文发送。
> **证书校验默认关闭**：目标与代理证书默认都不校验；TLS 代理（`https`/`socks5+tls`）如需开启校验，在代理地址追加
> `?tls-insecure-skip-verify=false`，并可用 `tls-ca-file=<CA路径>`、`tls-domain=<校验名>` 指定信任根与 ServerName。

### Raw HTTP 请求（精确控制原始报文）

```yaml
type: http
raw: |
  GET / HTTP/1.1
  Host: {{hostname}}
  User-Agent: gxx-fingerprint
  X-Custom: test
```

> `raw` 字段非空时优先走 `projectdiscovery/rawhttp`，可精确控制头部顺序、保留非常规字符，适合对协议格式敏感的指纹识别场景。

## 单条 Rule 的全部字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `request` | object | 上方四种请求模板之一 |
| `expression` | string | 单规则 CEL 表达式（必填）|
| `output` | map | 该规则匹配后向 varMap 注入的变量，用于后续规则引用（CEL 表达式形式）|

每条子规则使用一个 `expression`，多条件用 CEL 的 `&&`、`||` 组合。`output` 仅在当前子规则成功匹配时求值，只有成功提取的值才注入后续执行状态；提取失败不会把表达式文本当作提取结果。

### 产品版本

SDK 使用 `output.product_version` 回传被识别产品的版本，来源版本位于 `Info.Source.Version`。版本必须来自该产品的明确响应特征，不使用任意页面版本号或协议版本替代。以 nginx 为例：

```yaml
rules:
  r0:
    request:
      method: GET
      path: /
    expression: '"server" in response.headers && response.headers["server"].matches("(?i)^nginx(?:/|$)")'
    output:
      product_version: 'submatch("(?i)^nginx/(?<version>[0-9]+(?:\\.[0-9]+)+)", response.headers["server"])["version"]'
expression: r0()
```

响应只包含 `Server: nginx` 时仍可识别产品，版本保持为空。成功子规则提取出不同版本时，SDK 保留版本列表并设置 `VersionConflict`，不选取某一个版本冒充确定结果。版本最多 128 字节，不能包含换行或 NUL；公开输出采用有界文本副本，不持有完整正文。

示例 — 用 `output` + `submatch` 提取版本号供后续规则使用：

```yaml
rules:
  r0:
    request:
      method: GET
      path: /
    expression: response.raw_header.ibcontains(b"Server: nginx")
    output:
      ver: submatch("nginx/(?<v>[\\d.]+)", string(response.raw_header))["v"]
  r1:
    request:
      method: GET
      path: /admin
    expression: response.status == 200 && r0()  # r0 命中后 ver 才可用
expression: r0() && r1()
```

## 请求 / 响应对象属性

> 类型定义来自 `utils/proto/http.proto`（编译产物 `utils/proto/http.pb.go`），CEL 表达式中可直接通过字段名访问。

### request（proto.Request）

| 字段 | 类型 | 说明 |
|------|------|------|
| `request.url` | `UrlType` | URL 拆解结构，见下文 |
| `request.method` | string | HTTP 方法（如 `GET`） |
| `request.headers` | `map[string]string` | 请求头，key 一律小写；用 `in` 判断键存在 |
| `request.content_type` | string | `request.headers["content-type"]` 的快捷字段 |
| `request.body` | bytes | 请求体（GET 时为空） |
| `request.raw` | bytes | 原始请求报文 |
| `request.raw_header` | bytes | 原始请求头 |

### response（proto.Response，HTTP）

| 字段 | 类型 | 说明 |
|------|------|------|
| `response.status` | int32 | HTTP 状态码 |
| `response.url` | `UrlType` | 该响应所在页面的 URL |
| `response.headers` | `map[string]string` | 响应头（同 request.headers） |
| `response.content_type` | string | `Content-Type` 快捷字段 |
| `response.body` | bytes | 响应体 |
| `response.raw` | bytes | 原始响应（含头 + body） |
| `response.raw_header` | bytes | 原始响应头，按服务器发送的顺序逐行写出（名称为规范形式，多值头各占一行） |
| `response.icon_hash` | string | favicon mmh3 哈希（扫描入口页，或根路径 GET 的 HTML 响应） |
| `response.latency` | int64 | 响应延迟，单位毫秒（可用于异常分析） |
| `response.tls_version` | string | 响应所在连接的 TLS 版本，如 `"TLS 1.3"`；明文响应为空串 |
| `response.cipher_suite` | string | TLS 套件名称；明文响应为空串 |
| `response.ja3s` | string | 服务端 ServerHello 的 JA3S 摘要；明文响应为空串 |
| `response.jarm` | string | 目标的 JARM 指纹，引擎开启 JARM 时才有值，否则为空串 |

TLS 变量的来源与计算方式见 [TLS 信息与指纹](TLS信息与指纹.md)。

### UrlType（`request.url` / `response.url`）

| 字段 | 示例 |
|------|------|
| `scheme` | `"http"` / `"https"` |
| `domain` | `"example.com"` |
| `host` | `"example.com:8080"` |
| `port` | `"8080"`（注意是字符串） |
| `path` | `"/a/b"` |
| `query` | `"k=v&x=y"` |
| `fragment` | 锚点 |

### TCP/UDP / Raw 响应

- `response.raw` — 原始响应字节流（其他 HTTP 字段为零值）
- 经 TLS 建立的 TCP 连接同样提供 `response.tls_version`、`response.cipher_suite`、`response.ja3s`

## 表达式语法

### 匹配响应状态
```
response.status == 200
```

### 匹配响应体
```
response.body.bcontains(b"特征字符串")  # 二进制包含，区分大小写
response.body.contains("特征字符串")    # 字符串包含，区分大小写
response.body.ibcontains(b"特征字符串") # 二进制包含，不区分大小写（推荐）
```

### 匹配响应头
```
response.headers["Server"] == "Apache"
response.headers["Content-Type"].contains("json")
response.raw_header.bcontains(b"Server: Apache") # 使用原始响应头进行二进制匹配
response.raw_header.ibcontains(b"server: apache") # 使用原始响应头进行不区分大小写的二进制匹配
```

### 匹配图标哈希
```
response.icon_hash == "哈希值" # 入口页或根路径 GET 的 HTML 响应
```

### 匹配原始响应
```
response.raw.bcontains(b"特征字符串") # 二进制包含，区分大小写
response.raw.ibcontains(b"特征字符串") # 二进制包含，不区分大小写
```

### 正则表达式匹配
```
response.body.bmatches(b"正则表达式")
response.raw_header.bmatches(b"正则表达式")
```

### 组合表达式
```
条件1 && 条件2 # 与
条件1 || 条件2 # 或
!条件 # 非
```

## 辅助函数

> 以下是 GXX 当前 CEL 引擎实际暴露的所有函数（来自 `pkg/cel/celprogram.go`）。
> 文档外的函数（如 `sha1` / `sha256` / `randomAlpha` / `randomNumber` / `randomUppercase`）在 GXX 中**不存在**，请勿在规则中使用。

### 随机数 / 随机字符串

- `randomInt(min, max)` — `[min, max)` 范围内随机整数
- `randomLowercase(length)` — 指定长度的随机小写字母字符串

### 编码 / 哈希

- `base64(s)` / `base64(b)` — Base64 编码（接受 string / bytes）
- `base64Decode(s)` / `base64Decode(b)` — Base64 解码
- `md5(s)` — 32 位十六进制 MD5 字符串
- `hexdecode(s)` — 十六进制串解码为字符串
- `faviconHash(s)` / `faviconHash(b)` — favicon 内容的 mmh3 哈希（int64）

### URL 处理

- `urlencode(s)` / `urlencode(b)` — URL 编码（`url.QueryEscape`）
- `urldecode(s)` / `urldecode(b)` — URL 解码（`url.QueryUnescape`）

### 字符串处理

- `icontains(s, sub)` (string member) — 不区分大小写包含
- `substr(s, start, length)` — 截取 `[start, start+length)` 子串
- `replaceAll(s, old, new)` — 全部替换
- `printable(s)` — 仅保留可打印字符
- `toUintString(s, direction)` — 规范化数字字符串，`direction == "<"` 表示先反转

### 字节匹配

- `bcontains(b)` (bytes member) — 字节包含，区分大小写
- `ibcontains(b)` (bytes member) — 字节包含，不区分大小写（**推荐**）
- `bstartsWith(b)` (bytes member) — 字节前缀

### 正则

- `bmatches(pattern, b)` (string member) — 字节流正则匹配，返回 bool
- `submatch(pattern, s)` (string member) — 命名捕获字符串，返回 `map[string]string`
- `bsubmatch(pattern, b)` (string member) — 命名捕获字节流，返回 `map[string]string`

> 正则引擎是 `dlclark/regexp2`（兼容 .NET 风格），支持 `(?<name>...)` 命名捕获、零宽断言、回溯引用等。

### 时间（无参占位 `0`）

- `year(0)` — 当前年份 4 位（如 `"2026"`）
- `shortyear(0)` — 当前年份 2 位
- `month(0)` — 当前月份 2 位
- `day(0)` — 当前日期 2 位
- `timestamp_second(0)` — 当前 Unix 时间戳（秒，字符串）

### 杂项

- `sleep(seconds)` — 阻塞指定秒数（CEL 上下文中谨慎使用）

### 用 submatch 提取版本号（指纹细分）

```yaml

info:
  name: Nginx
  author: 作者名
  description: 识别 Nginx 并按版本号细分
  created: 2026/05/22

rules:
  r0:
    request:
      method: GET
      path: /
    expression: response.raw_header.ibcontains(b"Server: nginx")
    output:
      ver: submatch("nginx/(?<v>[\\d.]+)", string(response.raw_header))["v"]
  r1:
    request:
      method: GET
      path: /
    # ver 由 r0 的 output 注入，CEL 表达式可直接引用，便于按主版本号细分指纹
    expression: r0() && ver.startsWith("1.")

expression: r1()
```

## payloads 多组载荷

`payloads` 顶层字段用于在同一指纹下并行尝试多组变量（如多套常见路径、多个登录页特征），每组都会与下面的 `rules` 组合执行：

```yaml
payloads:
  continue: true       # true=命中后继续尝试下一组；false=命中即停
  payloads:
    set1:
      path: "/admin/login"
      keyword: "管理后台登录"
    set2:
      path: "/manage/login.html"
      keyword: "后台管理系统"

rules:
  r0:
    request:
      method: GET
      path: "{{path}}"
    expression: response.status == 200 && response.body.ibcontains(bytes(keyword))

expression: r0()
```

> 每个 set 块中的键会写回到 varMap，可用 `{{}}` 模板替换，也可在 CEL 中直接引用。
> 典型场景：同一 CMS 在不同部署下后台路径不同，可通过多组 path + 关键字共同提高识别覆盖率。

## 常见陷阱

1. **大小写敏感**：`response.headers` 的 key 在解析时统一转为**小写**；写 `response.headers["Server"]` 取不到值，应写 `response.headers["server"]`，或改用 `response.raw_header.ibcontains(...)`。
2. **`raw_header` 是 bytes**：必须搭配字节方法（`bcontains` / `ibcontains` / `bmatches`），不能用字符串方法。
3. **`response.body` 是 bytes**：同上。混用会触发 CEL 类型错误。
4. **不要在指纹中使用 `sleep(N)`**：会阻塞规则池 worker，影响整体扫描吞吐。
5. **不存在的函数**：`sha1` / `sha256` / `randomAlpha` / `randomUppercase` / `randomNumber` 等在 GXX 中**未实现**。请使用本文 §辅助函数 列出的真实函数。

## 最佳实践

- **规则命名**: 规则标识按“规则标识”一节由产品键派生，名称反映目标应用或服务
- **产品声明**: 每条规则声明 `info.product`；同一产品的多条规则复制完全相同的声明，参考链接只写确认过的官方地址
- **变量引用**: 使用 `{{变量名}}` 语法引用set中定义的变量
- **规则组合**: 使用逻辑操作符 `&&`（与）和 `||`（或）组合多个规则
- **文档完善**: 提供详细的描述和参考链接，便于他人理解和维护
- **测试规则**: 在提交前充分测试规则的有效性和准确性
- **规则分类**: 使用适当的标签对规则进行分类，便于检索
- **优先 ibcontains**: 字节匹配优先 `ibcontains`，规避大小写差异
- **`response.icon_hash` 使用范围**: 扫描入口页支持非根路径、跳转和 XHTML；其他规则响应仅在根路径 GET 的 HTML 场景抓取。范围与限制见 [网站元数据识别](网站元数据识别.md)

### 根据HTTP响应头识别服务器

      path: /
